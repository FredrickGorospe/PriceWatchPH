# TASK_004 — Derived schema: `Listing`, `PricePoint`, `DealFlag`, `Outcome`

`PricePoint` and `DealFlag` (a new `pricing` app), `Outcome` (a new
`outcomes` app) — so phase 1 ingestion has somewhere to land once resolved,
and phase 3/5/8 have somewhere to write, with every constraint from

**Out of scope for this task** — do not touch, do not scaffold, do not
anticipate:

  `Listing` — phase 3.

## 3. Acceptance criteria

Acceptance tests are written and approved here, before any implementation
exists, per the workflow in `CLAUDE.md`. All test functions below currently
fail — by collection/import error, since none of `listings`, `pricing`, or
`outcomes` exists yet. That is the required state. Implementation must make
them pass without modifying them; if a test turns out to be wrong, stop and
say so rather than editing it.

Six decisions precede the tests. The first four were previously tagged in
`docs/00_PLANNING.md` §5 as needing the user's answer, not a guess; the
other two follow the same "state the reasoning, don't invent policy"
discipline TASK_002/003 used for unenumerated vocabularies and `on_delete`
choices.

**Decision 1 — `Outcome.bought_at`/`sold_at`/`bought_price`/`sold_price`.**
Four fields: `bought_at`, `bought_price`, `sold_at`, `sold_price` — this was
the user's answer to `docs/00_PLANNING.md` §2's open question (`realised_margin`
needs purchase and sale amounts as inputs, and the roadmap's two-timestamp
wording alone doesn't supply them), not the two-field shape an earlier draft
of this task file used. All four are nullable: a skipped flag (`acted=False`)
has no transaction, so none apply.

`realised_margin` is a **`GeneratedField(db_persist=True)`**, computed by the
database as `sold_price - bought_price` (positive = profit, negative = loss),
not entered directly and not computed in Python at read time. This closes
the `docs/00_PLANNING.md` §5 "Django 5.2 specifics" Unknown from TASK_001
("whether `GeneratedField` is the right tool for `realised_margin`... and
what its Postgres stored-versus-virtual limitations are") with an actual
experiment against this repo's running stack, not an assumption:

- Postgres 16 only supports `STORED` generated columns (not `VIRTUAL`, which
  Postgres doesn't add until 18), so `db_persist=True` is the only valid
  choice here — verified by creating a scratch table via
  `connection.schema_editor()` with exactly this Django version.
- The expression correctly produces `NULL` when either `bought_price` or
  `sold_price` is `NULL` — the "not yet closed out, or skipped" case needs no
  special handling; ordinary SQL `NULL` arithmetic already does the right
  thing.
- Postgres itself rejects a direct write to the column —
  `UPDATE ... SET realised_margin = ...` raises
  `ProgrammingError: column "realised_margin" can only be updated to DEFAULT` —
  so the guarantee is enforced at the database level, the same standard this
  repo already holds `RawListing` immutability to (TASK_003), not merely a
  Python-level convention.
- Django's ORM does not raise if a caller passes `realised_margin=...` to
  `.create()` or `.update()` — it silently excludes the field from the
  generated `INSERT`/`UPDATE` SQL rather than erroring, so the value actually
  stored is always the database's computation, never the caller's. This is
  safe (verified: passing a bogus value at construction time did not
  persist), but worth knowing — no future code should rely on setting this
  field directly, since nothing will complain if it tries and nothing will
  happen either.

This choice follows `docs/00_PLANNING.md` §2's own stated rule directly:
"Database-level for anything that must hold regardless of how the row
arrived... Python-level for anything that needs application context."
`realised_margin` is pure arithmetic over two already-stored columns with no
policy or application context involved — squarely database-level territory
by the document's own reasoning, not a close call. A read-time-only Python
property was the alternative and is rejected here: it would need every
future consumer (admin, reports, any query that filters/sorts/aggregates by
margin) to either recompute it after fetching or repeat the same
`.annotate()` expression at each call site, multiplying the places the
sign convention or null-handling could drift, for no benefit over a
column that's simply always correct.

**Decision 2 — condition vocabulary.** `new` / `like_new` / `used` /
`for_parts`, from the user directly. `docs/00_PLANNING.md` §5 noted this
"matters more than it looks" since `condition` is part of the `PricePoint`
key, and also noted the answer "is not knowable until phase 1 data exists" —
that caveat was surfaced to the user before asking, and this is their answer
regardless, not a placeholder invented here.

**Decision 3 — `PricePoint`'s daily boundary.** `day` is the date portion of
`fetched_at` after converting to Asia/Manila, not the UTC calendar date, from
the user directly. `docs/00_PLANNING.md` §5 noted a UTC day splits a Manila
evening across two buckets. This decision governs *aggregation code* that
computes `day` from `fetched_at` (phase 5, out of scope here) — at the
schema level `PricePoint.day` remains a plain `DateField`, so this task
records the decision with a comment rather than enforcing it in SQL.

**Decision 4 — deal score representation.** `DealFlag.score` is a signed,
unbounded `Decimal`, in units of the baseline's MAD (median absolute
deviation): negative means the listing is priced below baseline (a deal),
and the magnitude is the distance from baseline in MAD units. From the user
directly, in response to `docs/00_PLANNING.md` §5's framing that TASK_004
must pick a representation before phase 5 settles the full semantics. The
column's exact numeric width (`max_digits=10, decimal_places=4`) is a
low-stakes technical default on top of that settled meaning — see Unknowns.

**Decision 5 — app placement.** `docs/00_PLANNING.md` §4 names
`pricing/models.py` and `outcomes/models.py` directly, so those two app
names aren't a decision made here, just the doc's own naming. `Listing`'s
location was left open ("`catalogue/models.py` or a `listings/` module")
— this task creates a new **`listings`** app, for symmetry with `sources`,
`catalogue`, and `ingestion` each already mapping 1:1 to a
`docs/ROADMAP.md` component; `Listing` belongs to "Normalisation + entity
resolution," a component distinct from "Catalogue."

**Decision 6 — controlled vocabularies not named in `docs/00_PLANNING.md`
§5's blocking list.** `Listing.resolution_method` uses
`exact_alias`/`fuzzy_match`/`human_confirmed` — §2 names these three
mechanisms directly in prose ("exact alias, fuzzy match, human
confirmation"), so this is a naming choice, the same way TASK_003 named
`SkuAlias.source_of_truth`'s two values from its own prose. `DealFlag.reason`
is different in kind: §2 describes it only abstractly ("the rule that
fired") and names zero concrete rule types anywhere, because phase 5 hasn't
defined any scoring rules yet. Inventing rule-name strings here would assert
phase-5 policy that doesn't exist, not just pick a naming convention for an
already-named set — so `reason` is a plain `TextField` with no `choices` or
`CheckConstraint` in this task; a vocabulary can be added later, without a
type change, once phase 5 defines actual rule types.

`on_delete` choices, reasoned individually: `Listing.raw_listing` and
`Outcome.deal_flag` are `OneToOneField`s — Django enforces the "one X per Y"
uniqueness directly (verified against this repo's actual Django 5.2.16
installation, not assumed) — with `on_delete=PROTECT`, since a resolved
listing or a logged outcome shouldn't silently vanish. `Listing.sku` is
`SET_NULL` (already nullable, for the review queue: if the `Sku` a `Listing`
pointed to were ever deleted, the `Listing` reverts to unresolved rather than
disappearing). `PricePoint.sku`, `DealFlag.listing`,
`DealFlag.baseline_pricepoint`, and `Outcome.deal_flag` are all `PROTECT` —
none of these should silently cascade-delete history.

**Correction found during implementation:** this task file originally stated
that `PricePoint.n_listings >= 0` needed an explicit `CheckConstraint`
because `PositiveIntegerField` does not auto-generate a database-level
`CHECK`, based on a grep of the ORM field class and the Postgres schema
backend that turned up nothing. That grep was incomplete. Inspecting the
actual migrated schema (`\d pricing_pricepoint`, `\d outcomes_outcome`)
during implementation showed **two** `CHECK` constraints on each
`PositiveIntegerField` column — the explicit one from this task's
`Meta.constraints`, and a second, Postgres-auto-named one
(`pricing_pricepoint_n_listings_check`, `outcomes_outcome_days_held_check`).
Tracing it further: `PositiveIntegerField.db_parameters(connection)` returns
`{'type': 'integer', 'check': '"n_listings" >= 0'}` — Django's schema editor
embeds this as an inline `CHECK` in the column's own DDL (via
`Field.db_check()`), which is why grepping for a separate `CheckConstraint`-style
mechanism in `schema.py` found nothing: it isn't one, it's part of
`column_sql()`. So `PositiveIntegerField` **does** enforce `>= 0` at the
database level on its own, in this Django version. This task's explicit
`CheckConstraint`s on `n_listings` and `days_held` are therefore harmlessly
redundant, not load-bearing as originally claimed — kept anyway, since
"explicit over clever" per `CLAUDE.md` favors the intent being visible in
the model file rather than relying on an implicit field-type behavior a
reader would have to already know. This also means TASK_002's
`Source.rate_limit` constraint was never strictly necessary either, for the
same reason — harmless there too, and not worth an unrelated retroactive
change.

```python
from django.db import models
from django.db.models import F, Q

from pricing.models import DealFlag


class Outcome(models.Model):
    deal_flag = models.OneToOneField(DealFlag, on_delete=models.PROTECT, related_name="outcome")
    acted = models.BooleanField()
    skip_reason = models.TextField(null=True, blank=True)
    bought_at = models.DateTimeField(null=True, blank=True)
    bought_price = models.DecimalField(max_digits=12, decimal_places=2, null=True, blank=True)
    sold_at = models.DateTimeField(null=True, blank=True)
    sold_price = models.DecimalField(max_digits=12, decimal_places=2, null=True, blank=True)
    days_held = models.PositiveIntegerField(null=True, blank=True)
    # Database-computed, not entered directly (see Decision 1) — verified
    # against this repo's actual Django 5.2.16 + Postgres 16 that
    # GeneratedField(db_persist=True) here: propagates NULL correctly when
    # either price is missing, is rejected as an UPDATE target by Postgres
    # itself, and is silently excluded (not errored) by Django's ORM if a
    # caller tries to set it directly. Signed: losses are the most
    # informative rows and must be storable.
    realised_margin = models.GeneratedField(
        expression=F("sold_price") - F("bought_price"),
        output_field=models.DecimalField(max_digits=12, decimal_places=2),
        db_persist=True,
        null=True,
        blank=True,
    )

    class Meta:
        constraints = [
            models.CheckConstraint(
                condition=Q(acted=True) | (Q(skip_reason__isnull=False) & ~Q(skip_reason="")),
                name="outcome_skip_reason_required_when_not_acted",
            ),
            models.CheckConstraint(condition=Q(days_held__gte=0), name="outcome_days_held_non_negative"),
        ]

    def __str__(self):
        return f"Outcome #{self.pk} (acted={self.acted})"
```

of these apply. Only the `skip_reason` implication is an explicit
`docs/00_PLANNING.md` §2 requirement — no additional constraint is invented
tying `acted` to whether the other fields are null, since that isn't stated
anywhere.
